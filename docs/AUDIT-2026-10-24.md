## 0. Answer to the standing question

> "does the code enforce its fail-closed guarantees under unexpected conditions?"

**Partially — at the unit level yes, at the system level no.** Every individual gate function
degrades closed when *its own boolean inputs are honest* (`g1`–`g11` all return FAIL/UNKNOWN on
falsy), but the three components that could turn failure into READY are fail-open or unimplemented:

1. **`aggregate()` has a fail-open default** (§F-01). Any unrecognized gate status string falls
   through to READY. `undefined`, `'PASS '`, `'pass'`, or a typo → verdict `READY`.
2. **The READY invariant is never enforced** (§F-02). `readyInvariant()` exists, is imported,
   and is never called. `assess()` never validates decoder+state-verified effects.
3. **L2 verify does not re-derive the verdict** (§F-03). A forged-but-hash-consistent receipt
   passes L1 *and* L2, which is exactly what SPEC §10 says L2 must catch.

Today the shipped `assess()` cannot emit READY at all (its gate inputs are hardcoded
failing/unknown literals — see §F-08), so the practical risk is not "READY leaks out today";
it is that **the two components whose job is to guarantee fail-closure are the broken ones**,
and full engine functionality is claimed in README/CHANGELOG while unimplemented.

## 1. Findings — security (paths toward a wrong READY)

### F-01 · CRITICAL — fail-open default in verdict aggregation
`src/verdict.ts:1-6`
```ts
export function aggregate(gates: { status: string }[]): string {
  if (gates.some((g) => g.status === 'FAIL_HARD')) return 'BLOCKED';
  if (gates.some((g) => g.status === 'UNKNOWN')) return 'HUMAN_REVIEW';
  if (gates.some((g) => g.status === 'FAIL_TRANSIENT')) return 'DEFER';
  return 'READY';
}
```
Anything that is not one of the three recognized failure literals contributes to READY:
`'NOT_APPLICABLE'` (fine), but also `'PASS '` (space), `'pass'`, `undefined`, `'SKIPPED'`,
or any probe code that forgets to set status. SPEC §9 defines a closed status set; the
codifier of that set (`src/types.ts:4`) exists but `aggregate()` takes `{ status: string }`.

*Exploit narrative:* any future wiring (probe scripts, M8/M9 gates, diagnostics that push
partial gate objects) that produces a gate with an unconventional status lets all other gates
PASS → `READY` with zero decoder or simulation evidence.
*Fix:* normalize first —
```ts
export function aggregate(gates: GateResult[]): Verdict {
  const known = (s: string) =>
    s === 'PASS' || s === 'NOT_APPLICABLE' || s === 'FAIL_HARD' ||
    s === 'FAIL_TRANSIENT' || s === 'UNKNOWN';
  if (gates.some((g) => !known(g.status))) return 'HUMAN_REVIEW'; // treat as UNKNOWN
  ...same precedence...
}
```
Also: require the expected gate set to be present (or explicitly `NOT_APPLICABLE`); an
*absent* gate is not a passing gate. Return the typed `Verdict`, not `string`.

### F-02 · CRITICAL — READY invariant defined, never enforced
`src/verdict.ts:8-10` defines `readyInvariant()`; `src/assess.ts:16` imports it; nothing calls it
(verified by grep over `src/`). SPEC §9/§13/§14.6 requires: no READY without (a) supported decoder,
(b) state-verified effects, (c) resolved critical assumptions, enforced by *code and tests*.
Additionally SPEC §13 requires a test that "no code path can emit READY without a decoder result
and state-verified effects" — no such test exists (grep over `tests/` for READY yields only
hash fixtures and `aggregate([{status:'PASS'}]) === 'READY'` unit assertions).

*Fix:* make `aggregate` take `{ decoderOk: boolean; g8Pass: boolean; unresolvedAssumptions: number }`
(or have `assess()` compute it) and hard-code: `verdict === 'READY'` requires `readyInvariant`.
Add the property test. Add the adversarial test: decoderRes.ok === false → must never be READY;
g8 not available → must never be READY.

### F-03 · CRITICAL — L2 verify does not re-derive the verdict
`src/verify.ts:7-13`:
```ts
export function verifyL2(receipt: any): VerifyResult {
  if (!receipt.inputs || !receipt.evidence) return FAIL;
  const gates = receipt?.assessment?.gates ?? [];
  const m8m9 = gates.filter((g) => g?.gate === 'G11_LENDING' || g?.gate === 'G12_SMART_ACCOUNT');
  if (m8m9.some((g) => g.status !== 'PASS')) return FAIL;
  return { level: 2, result: verifyHashes(receipt) ? 'PASS' : 'FAIL' };
}
```
L2 = "hashes recompute + G11/G12 pass". It never replays the assessment against
`receipt.inputs` + `receipt.evidence` via `ReplaySource` and never compares the verdict.
Consequences:
- A hand-built receipt: `verdict: 'READY'`, gates all `FAIL_HARD`, evidence `[]`, hashes
  recomputed with this library's own `buildReceipt` → **L1 PASS, L2 PASS**. The one SPEC
  promise that differentiates this project ("verify re-derives the verdict offline") is not met.
- Gates missing entirely → `filter` yields `[]` → check vacuously passes.
- The only non-hash check (G11/G12) fails-open on absent gates, same pattern as F-01.

*Fix:* L2 = rebuild assessment from `receipt.inputs` + `receipt.evidence` through the same
gates (offline, deterministic), compare verdict + reasons + gate statuses byte-for-byte;
missing evidence → `EVIDENCE_INCOMPLETE` FAIL, per SPEC §10 self-containment rule.
`ReplaySource` already exists (`src/evidence.ts:66`) and is currently unused by `verify`.

### F-04 · HIGH — G8 "state-verified effects" is unimplemented
`src/simulator.ts` is an interface with no implementation; grep shows no `eth_simulateV1`,
no prestateTracer, no balance/allowance diff code anywhere in `src/`. `g8Simulation()`
receives booleans whose only producers are hardcoded literals in `assess.ts:47`.
The verifier of the entire value proposition (S27, S28, "effects verified from simulated
STATE") does not exist. note.md documents the M0 go/no-go probe succeeded, so the evidence
path is known-feasible — it just was never built.
*Fix:* implement the simulator (sequential `eth_simulateV1` state reads as probed), wire its
result into `g8Simulation`, and add the S27/S28 fixtures. Until then, `guarantees.enforced`
must be empty, not implied, and README claims must be downgraded (see §F-08/P-01).

### F-05 · HIGH — G7 (decode gate) missing; decoder results discarded
`src/assess.ts:30-37` computes `decoderRes` and **never uses it**: no `G7_DECODE` gate is
pushed (SPEC §8 requires it), no FAIL on `ok:false`, no G10 checks derived from decoded
`minAmountOut`/`recipient`/`deadline`/poolKey. G10 receives hardcoded booleans (`assess.ts:57`).
Reason codes `DECODE_MISMATCH` (intent cross-check), `DEADLINE_MISSING/TOO_FAR`,
`NOTIONAL_EXCEEDS_POLICY`, `POOL_NOT_ALLOWED`, `POOL_FEE_EXCEEDS_POLICY` exist in
`src/reasons.ts` but are emitted from nowhere (grep-verified).
*Fix:* push G7 from `decoderRes` (ok:false → severity from reason), derive G10 inputs from
`decoded.*`, implement the intent cross-check (S22) and deadline/pool checks.

### F-06 · HIGH — router codehash is a caller-supplied magic value
Both decoders compare `routerCodehash` against caller-supplied `supportedCodehashes`
(`src/decoders/universal-router-v4.ts:40`, `src/decoders/swap-router02.ts:34`). Nobody computes
the codehash from the target's bytecode: no `eth_getCode` anywhere in the assess path.
`assess.ts:35-36` passes `'0x0'` as both the codehash *and* its own supported list — the
comparison is therefore a tautology: any `to` + any `execute(bytes,bytes[],uint256)`-shaped
calldata with a single `0x10` command decodes "successfully" and would be labeled
`routerCodehash: '0x0'` in the receipt as if format-supported.

Good counterexample inside the repo: `swap-router02.ts:5-6` pins address+codehash verified by
`docs/probes/swap-router02-codehash.json` (VERIFIED, block 0x5a16b7b, 2026-10-21) — but that
verified decoder is used nowhere (grep: only its own definition).
*Fix:* assess reads `eth_getCode` at the pinned block (keccak → codehash as an
`onchain-reverifiable` evidence item), compares against the registry's verified constants;
unknown → `CODEHASH_UNKNOWN` → UNKNOWN/HUMAN_REVIEW per SPEC G7.

### F-07 · HIGH — UR decoder fabricates `recipient` and labels nothing
`src/decoders/universal-router-v4.ts:146`: `recipient: input.account` — hardcoded, not decoded.
The `tx-enforced` recipient guarantee (SPEC G7/G10, `allowedRecipients`) is enforced against a
value the library *asserted*, not extracted. A future wiring that trusts "decoded recipient"
for G10 would check the wrong field of a real transaction. (UR V4-swap output routing is a
settle path that needs its own handling; if it cannot be asserted from calldata, it must not
be claimed as tx-enforced.)
*Fix:* decode the actual output recipient per UR v4 semantics, or report
`recipient: null` + `NOT_APPLICABLE` for the recipient check and drop the claim from
`guarantees.enforced`.

### F-08 · HIGH (honesty) — the shipped engine is a failing-inputs scaffold presented as complete
`assess.ts` hardcodes `g1Asset({inRegistry:false...})`, `g2Sequencer({feedKnown:false...})`,
`g5Issuer({stale:true...})`, `g8Simulation({available:false...})`, `g10Policy({tokenAllowed:false...})`
— so the tool structurally cannot produce READY (this is *accidentally* fail-closed) and cannot
produce most BLOCKED verdicts either (no gates receive real probe data). Yet:
- README claims "Verifies asset identity, oracle, corporate actions, issuer signals…
  Returns READY only for supported formats with state-verified effects" (README:13-15).
- README:29-56 teaches integration against `assess` with a UR address, implying it functions.
- CHANGELOG v0.2.0 says "M0-M7 initial implementation"; DRIFT-LIST itself records that STATUS
  overstates completion. DRIFT-LIST is honest; README is not.

*Fix:* README "What it does" must mirror DRIFT-LIST: implemented = gates as pure functions,
receipts, verify L1/L3-hash; unimplemented = registry probing, G7 wiring, simulation, policy
checks. Mark `assess()` with a docstring/exception when `limitations` includes
'minimal assess implementation'.

### F-09 · MED-HIGH — degraded G2 can PASS with `up: false` and no feed
`src/gates/g2.ts:2-7`: with `sequencerAssurance: 'degraded'` and `feedKnown: false`,
if header-gap signals look clean → status `PASS`, enforcement `advisory`.
SPEC G7 mapping says feed unknown → `UNKNOWN`; SPEC §9 says READY requires evidence per policy.
The strict-mode path correctly returns UNKNOWN (`g2.ts:9`), so this only weakens the verdict
if the caller chooses `degraded` — but that is policy-controllable input (via `Policy`),
and `g2-degraded.test.ts` locks PASS in. DECISIONS.md:32-33 records human authorization
("enable experimental degraded-mode PASS with conservative thresholds; observe-only by
default"), so this is an *authorized* deviation, but it should be scaled to the READY
invariant: degraded PASS must (a) surface in `limits/limitations` of every receipt it affects
(g2 does add `limitations` on the gate result, good), (b) never contribute to READY until
thresholds come from recorded probe data, and (c) `sequencerAssurance: 'degraded'` should
require signed policy provenance to differ from the strict default.
*Fix:* keep, but gate on `policyProvenance.operatorPolicyHash` being present; document in
SPEC as amendment (AMENDMENT-001 already exists — link it from SPEC §8).

### F-10 · MED — `policy-loader` "hash" is base64, and provenance binding is decorative
`src/policy-loader.ts:8`: `hash = Buffer.from(raw).toString('base64')` — an encoding, not a
commitment; `policyProvenance.ts` just relabels it. `loadOperatorPolicy` also accepts any env
name and never validates the file against `PolicySchema` (`src/schemas.ts` is unused — grep
shows no `validate(` caller). *Fix:* `sha256Hex(canonicalize(policy))`, validate with
`PolicySchema`, and put the verified hash into `inputs.policy` snapshot comparisons.

### F-11 · HIGH — credential-leak path in MCP/CLI policy loading
`loadOperatorPolicy(envName)` resolves **any** environment variable as a *path*, then
`JSON.parse`s it. Chain: `policyEnv = 'RHC_RPC_URL'` (an env var holding the credential-bearing
RPC URL per the repo's own convention) → `readFileSync(urlString)` throws
`ENOENT ... open 'https://provider.tld/v3/<API-KEY>'` → in `mcp-server.ts:33-35`
`catch (e) { process.stdout.write(JSON.stringify({ error: e?.message })) }` → the URL with its
key is written to stdout. `redactText()` exists (`src/redact.ts`) and is applied only inside
`LiveSource`, not here. Same unsanitized-error path in `cli.ts`. This violates the repo's own
hard rule (AGENTS.md: "never write URLs with path/query/credentials to any file, log...").
*Fix:* wrap `readFileSync`/`JSON.parse` in try/catch, pass `redactText(String(e?.message))`,
never echo the path; restrict policyEnv to names matching `^[A-Z][A-Z0-9_]*POLICY.*$`;
add a test asserting no `https?://` in any error output (the fixture exists for S32 — extend it).

### F-12 · MED — L3 verify checks one item and calls it done
`src/verify.ts:14-24`: re-fetches only `eth_getBlockByNumber` and compares `hash`; on network
errors returns `SKIPPED` (masking failure), never iterates the receipt's `onchain-reverifiable`
evidence, never reports "checked n of m" (SPEC §10). An evidence item whose block/envelope was
never checked is implicitly presented as fine. *Fix:* iterate rpc-class evidence, re-issue each
`request` at the pinned block, return per-item PASS/FAIL + counts; reserve SKIPPED for
`rpcProvided === false` only, never for exceptions mid-check.

### F-13 · MED — float math in lending (violates "all money math is bigint")
`src/lending.ts:13-14`: `Number(ltv) > input.ltvBps` mixes bigint→float. Precision loss for
large collateral values can flip an LTV check across the boundary in either direction.
Also `input.ltvBps` is compared against both thresholds and the computed ratio, so a caller
can set `ltvBps: 20000` and defeat both liquidation-threshold intent and policy intent depending
on order. *Fix:* compute `ltvBpsBig = borrowedValue * 10000n / collateralValue` and compare
bigint-only; split `policyLtvBps` from the liquidation/collateral-factor inputs.

### F-14 · MED — policy input is unvalidated on every real entrypoint
`assess.ts:19` takes `policy: any`; `mcp-server.ts:22` spreads `req.params` straight in;
`PolicySchema` (`schemas.ts`) is never used; `maxNotionalQuote` (the notional cap, S19) is
missing from the schema entirely. A malformed number (`"maxDeadlineSec": "300"` string) compares
with `<`/`>` producing string-coercion behavior. *Fix:* validate at the boundary; reject
unknown/missing critical fields (fail-closed) rather than defaulting silently.

### F-15 · LOW — deadline handling diverges from SPEC
UR decoder `execute(bytes,bytes[],uint256)` variant decodes deadline; the 2-arg variant forces
`deadline = 0` (`universal-router-v4.ts:80`) with no DEADLINE_MISSING mapping; G10 has no
deadline check at all (parameter does not even exist in `g10Policy`). `Number(bigint)` on a
>2^53 deadline becomes Infinity, which happens to fail safe. *Fix:* fold into F-05 G10 work.

### F-16 · LOW — session calendar errors are invisible to G3
`src/session.ts:8` window is 13:00–21:00 UTC with a comment admitting the simplification
(real NYSE is 13:30–20:00 UTC, and DST moves it); no holiday calendar (O10 ASSUMED, correct).
Worse: `g3Oracle()` has no `known` input, so `MARKET_CALENDAR_UNKNOWN` (S18) can never be
emitted — calendar uncertainty silently collapses to "off-session". *Fix:* thread
`inSession.known` through G3 and emit `UNKNOWN MARKET_CALENDAR_UNKNOWN` when unknown.

## 2. Findings — code quality

- **Q-01 (HIGH):** `verify.ts` operates on `any` end-to-end and duplicates receipt logic rather
  than sharing `buildReceipt`'s derivation path; with F-03 fixed the shared path is the point,
  so this consolidates.
- **Q-02 (MED):** ~40 `as any` casts concentrated in `assess.ts` and every gate return
  (`src/gates/*.ts` each build the result object `as any`). Gates have no shared `GateResult`
  shape enforcement — this is precisely the hole that lets F-01's status-string drift slip
  through. One `GateResult` type + constructor helper removes the entire class.
- **Q-03 (MED):** Test corpus: 40 files / 83 tests, all green, but coverage is hash-mechanics
  and per-gate boolean units. Zero tests assert *system-level* verdicts for scenario S01/S07
  etc. (s36-s38 "synthetic" tests exist for a handful). The mutation suite only mutates receipt
  fields. What is missing per SPEC §13: property tests for bigint valuation (none), the
  "no READY without decoder+effects" test (F-02), S14/S22 decode-vs-intent (decoder results
  unused → impossible), S19/S26 (reasons never emitted).
- **Q-04 (LOW):** `meter.ts` marks every Sourced value `state: 'NORMAL'`, `ageSec: 0`,
  `evidenceClass: 'onchain-reveriable'`-by-hand even for the `rpc:quote` entry fed by synthetic
  literals; `meter-api.ts` serves fully synthetic data under chain 4663/blockNumber '1'.
  `meter-strings.ts` `{above|below}` alternation syntax is unimplemented. All scaffold, but the
  meter's false `NORMAL` labels deserve a `NOT_ASSESSED` default.
- **Q-05 (LOW):** `evidence.ts:48` uses `Date.now()` — legal (SPEC rule ties capture time into
  evidence), but `headLagSec(blockTimestamp, captureUnix)` (`sequencer-signals.ts:10`) can be
  negative against a soft-confirmed head; `g2` threshold check would then pass trivially. Clamp
  or record negative lags as a signal.
- **Q-06 (LOW):** `canonical.ts` — correct for the used subset (`-0` serializes as `0`,
  ES6-style numbers match JCS), but 73-bit+ numbers in JSON would already have lost fidelity
  before canonicalization because callers build objects with `JSON.parse`. Money valuestravel
  as decimal strings in `Sourced<string>`/inputs — keep it that way and add a guard test that
  no receipt field path contains a money `number`.
- **Q-07 (LOW):** Dead code with safety implications: `ReplaySource` (unused), `verifyReceiptSignature`/
  `signReceipt` (v0.2 noted unsigned; fine), `decodeSwapRouter02` constants (the one verified
  router), `DEADLINE`/`NOTIONAL` reason codes. Some are "planned", but dead constants of a
  *verified* router suggest the intended wiring was abandoned mid-step — see F-05/F-06.
- **Q-08 (LOW):** Dependencies: `viem ^2.21.0` unpinned caret, `zod ^4.6.7` (zod v4 fine),
  `eslint ^10.13.0` — all caret ranges contradict SPEC §12 "pinned" and DECISIONS "pin versions".
  Lockfile constrains installs, but CI reproducibility and duplicate-lockfile drift argue for
  exact pins. No install-script deps (`pnpm.onlyBuiltDependencies: []` — good). npm-audit run
  now; not run for this audit (offline constraint), listed as follow-up.
- **Q-09 (INFO):** Secret hygiene: repo complies — `.env`-style URL never appears in fixtures
  (only `host` in `docs/probes/*.json`), `redact.ts` fallback regex is host-extracting, README
  uses a placeholder address. The F-11 path is the one real leak vector found.

## 3. Findings — product assessment

- **P-01 (buffered):** The *only* differentiating claim ("replayable, tamper-evident,
  re-derivable verdict") is the one to which L2 currently does not implement (F-03). Adjacent
  tools (Collar Guardrail, KeeperHub, rhc-mcp, zerouter — `docs/LANDSCAPE.md`) provide gates
  without replay; if this ships as "M8/M9 complete" and a consumer discovers L2 passes forged
  receipts, the trust story is worse than never claiming it. The reviewer's caution is correct
  — not as sole security control, and today it would be *more* honest to ship it explicitly as
  "gate library + receipt format, engine in progress".
- **P-02:** The scenario suite (S01–S32) remains the strongest asset: it sets a falsifiable
  bar and most failing scenarios correspond 1:1 to gate functions that exist and behave
  fail-closed on their inputs. The gap between "gate exists" and "gate is fed" is the whole
  remaining engine work (F-04..F-06, F-08).
- **P-03:** Positioning vs. Collar/KeeperHub: those gate *their own* execution; this gates
  *someone else's* calldata with receipts. Replay is worth building to completion before
  breadth (lending M8 / smart account M9 are already marked experimental in README, correctly).

## 4. Minimal order of attack (fix proposals, conservative)

1. F-01 + F-02 + F-05 + F-06 (one PR): status normalization, READY invariant enforcement,
   G7 gate + G10-from-decoded wiring, codehash from `eth_getCode`. Failing tests first
   (verdict-level, not gate-level).
2. F-03: L2 re-derivation via `ReplaySource` + verdict comparison + `EVIDENCE_INCOMPLETE`.
   Mutation suite extension: flip any gate inside a receipt → L2 FAIL.
3. F-11 (+F-10): redact policy-loading errors, real sha256 provenance, PolicySchema validate.
4. F-04: implement the simulator with the M0-verified `eth_simulateV1` pattern; only then do
   README claims match reality (P-01).
5. F-12, F-13, F-14, F-16, Q-0x as hygiene PRs.

## 5. What was tried but not found exploitable

- Gate-level fail-open: all 11 gates return FAIL/UNKNOWN on falsy inputs — no boolean-coercion
  holes found in the gate bodies themselves (`if (!x)` chains are directionally safe).
- Float leakage into money math: only F-13. canonicalization of bigint is string-safe.
- Untrusted-string interpolation: gate details dictionaries contain booleans/objects only;
  reason codes are a fixed table (`reasons.ts`); error messages from RPC are redacted in
  LiveSource. The one unredacted sink is F-11.
- Signed-receipt path (`sign.ts`): not wired into assess/verify, so no bypass surface yet;
  payload canonicalization reuses `canonicalize` correctly.
- Big endian of gate order / duplicate gates: `aggregate` scans all gates regardless of order
  or duplicates — duplicates of a failing gate cannot rescue a passing one by construction
  (it is the missing/typo'd ones that can, F-01).
